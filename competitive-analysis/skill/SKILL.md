# 竞品分析研究

## 核心目标

把用户的竞品调研请求转化为一套可解释、可验证、可复用的研究流程。

不要从“有哪些热门竞品”开始。先回答：
1. 用户真正想通过竞品研究解决什么问题；
2. 哪类竞品最能回答这些问题；
3. 这个产品类型是否已有成熟的研究框架、UX benchmark 或设计范式；
4. 哪些结论有一手证据支持；
5. 最终这些结论对目标产品意味着什么。

最终必须交付一个**本地可直接打开的 HTML 报告**。

---

# 工作流

## Step 1｜判断需求清晰度

先分类：

### 模糊需求
例如：
- “帮我看看这个方向有哪些竞品”
- “分析一下 AI 3D 产品”
- “看看同类产品怎么做”
- 用户只给了目标产品，没有给研究问题

处理：
1. 推导 2–4 个研究问题；
2. 用一句话说明研究目标；
3. 不立即做深度研究。

### 明确需求
例如：
- 用户已经指定竞品；
- 指定了分析维度；
- 指定了任务链、功能或交互问题；
- 指定了报告结构。

处理：
- 保留用户已有 scope 和术语；
- 只对重叠 / 冲突的维度做归一；
- 不重复询问已经明确的信息。

---

## Step 2｜识别产品类型，并搜索成熟研究框架

这是强制步骤。

不要默认套 Agent 框架。

先判断目标属于哪类产品，例如：
- 电商 / 零售
- B2B / SaaS / 数据工具
- 内容创作 / 设计工具
- AI / Agent
- 社交 / 内容社区
- 金融 / 支付
- 服务型产品
- 游戏 / 游戏工具
- 搜索 / 信息获取
- 移动应用 / 消费工具
- 其他垂直领域

然后上网搜索当前领域已有的成熟方法，优先：
1. 官方 / 研究机构 UX benchmark；
2. 大型设计团队公开方法；
3. 经过市场验证的设计框架；
4. 高质量设计师 / 产品文章；
5. 学术研究。

不要为了“看起来有框架”而强行套用。

如果领域已有成熟 benchmark，应优先吸收它的维度，再结合当前研究目标裁剪。

详见：
[references/framework-discovery.md](references/framework-discovery.md)

---

## Step 3｜定义研究问题

研究问题优先来自：
1. 用户明确的问题；
2. 目标产品当前决策；
3. 所选成熟框架；
4. 产品类型特有任务链。

如果研究对象是 Agent / AI workflow，可调用：
[references/agent-product-framework.md](references/agent-product-framework.md)

不要把 Agent 的 G1/G2/G3 强行用于所有产品。

---

## Step 4｜生成候选竞品池

在深度研究前，先生成候选池。

候选分三类：
- **直接竞品**：用户、任务、环境高度重合；
- **邻近竞品**：任务相似，但环境 / 形态不同；
- **成熟类比产品**：不同垂类，但某个交互机制已被市场验证。

候选池通常 6–12 个。

每个候选给出：
- 产品名；
- 为什么相关；
- 主要回答哪个研究问题；
- 是否有丰富一手资料 / 截图；
- 不确定点。

---

## Step 5｜竞品选择必须经过用户确认

这是强制检查点。

先给用户一个简洁 shortlist，让用户自己快速看。

不要在用户尚未确认时，就花大量时间生成完整报告。

推荐话术：

> 我先圈了一组候选，你不用详细体验，只需要快速判断哪些看起来最接近你想研究的问题。确认后我再深挖，避免在不合适的竞品上浪费时间。

如果用户已经指定竞品：
- 仍检查是否覆盖所有研究问题；
- 检查是否有重复样本；
- 必要时补充 1–3 个成熟类比产品。

竞品筛选规则详见：
[references/competitor-selection.md](references/competitor-selection.md)

---

## Step 6｜给每个竞品分配角色

不是所有产品都需要完整拆解。

可分：
- 核心垂直样本
- 核心成熟样本
- 交互补充样本
- 恢复 / 历史专项样本
- 产物编辑专项样本
- Automation 专项样本
- 其他专项样本

用矩阵说明“哪个产品回答哪个问题”。

---

## Step 7｜证据优先研究

证据优先级：

1. 当前官方 Docs / 官方产品页 / Changelog；
2. 用户提供的当前截图；
3. 官方帮助中心 / Release notes；
4. 高质量设计师 / 产品分析；
5. 论坛与第三方截图；
6. 明确标注的推断。

如果用户给了当前截图，当前 UI 分析优先使用用户截图。

不要用旧文档截图描述当前 UI。

详细规则：
[references/evidence-rules.md](references/evidence-rules.md)

---

## Step 8｜建立分析框架

框架必须和研究目标一致。

优先使用：
- 当前垂类已有成熟框架；
- 再结合用户问题裁剪；
- 最后才使用通用 UX 维度。

如果没有成熟框架，再自建。

自建时至少区分：
- 用户 / 任务
- 产品机制
- 交互呈现
- 结果 / 验证
- 差异化价值

Agent 类产品使用专项参考：
[references/agent-product-framework.md](references/agent-product-framework.md)

---

## Step 9｜先做跨产品结论，再写长篇产品详情

推荐顺序：

1. 研究目标
2. 研究范围与样本角色
3. 分析框架
4. 跨产品综合结论
5. 设计结论
6. 核心产品证据
7. 补充样本
8. 下一步研究

这样产品详解是“证据”，而不是一长串 Feature List。

---

## Step 10｜设计结论只能有一套

避免：
- 前后重复两套结论；
- 同一内容被分到不同优先级；
- Automation 一会儿是 baseline，一会儿是 future。

建议分：
- **体验基线**
- **差异化机会**
- **远期探索**

如果同一个结论出现在两个层级，必须先解决冲突再输出。

---

## Step 11｜截图与结论必须一一对应

强规则：

> 分析什么，图里就必须出现什么。

禁止：
- 用首页图讲恢复；
- 用聊天图讲 Task Board；
- 同一张截图反复证明多个无关结论；
- 有官方图不用，却用来源不明的第三方图。

图片、Logo 与本地 HTML QA：
[references/evidence-rules.md](references/evidence-rules.md)

---

## Step 12｜输出本地 HTML

最终报告必须：
- 白底；
- 信息层级清晰；
- 长报告优先固定侧导；
- 证据图优先 2 列，避免 4 列把图压小；
- 图片支持点击放大；
- UI 截图 `object-fit: contain`；
- 关键用户截图和不稳定 Logo 尽量本地化 / 内嵌；
- 公开 Docs 图片可外链，但必须检查是否能加载；
- 不显示任何内部修改意见、debug 信息、生成过程语言。

HTML 基础模板：
[assets/report-template.html](assets/report-template.html)

---

## Step 13｜报告结尾必须包含下一步研究

分两条：

### 纵向深入
继续拆核心竞品的：
- 状态变化
- 信息层级
- 任务细节
- 权限
- 异常
- 验证
- 恢复
- 边界场景

语气使用：
> 继续拆解核心机制与关键设计细节

避免：
> 直接进入设计

### 横向补充
只针对仍没有成熟答案的具体问题扩样。

不要为了增加竞品数量而扩样。

---

# 停止扩样的条件

满足以下条件时，停止继续找竞品：
- 多个成熟产品开始重复同一模式；
- 新样本没有新增机制或交互解法；
- 当前证据已经足以支持设计判断。

此时转向纵向深入。

# 典型调用

### 模糊需求
> @竞品分析研究 帮我看看 AI 3D 生成工具的竞品。

先定义问题，再给候选竞品，不直接生成大报告。

### 明确需求
> @竞品分析研究 对比 Aura、Unity AI Assistant 和 Codex，重点分析任务上下文、执行过程和恢复。

直接沿 scope 建框架，但仍检查样本是否足够。

### 非 Agent 产品
> @竞品分析研究 帮我分析生鲜电商 App 的竞品，重点看首页、搜索、商品详情和下单链路。

先搜索当前电商 UX benchmark / 成熟研究框架，再形成适合电商的分析维度；不要套 Agent 框架。
