# Research Packet — Design-System Doctor

Checked: 2026-08-14
Status: ready for skeleton v0.3 decisions

## Question
What can be validated mechanically, and what must remain a rendered or human review step?

## Local evidence
- `our-ui/scripts/check-component-coverage.mjs`: validates component coverage and specific hard constraints.
- `our-ui/scripts/qa-ui.mjs`: performs rendered browser checks across page/component documentation and layouts.
- `our-ui/system.manifest.json`: requires both coverage and UI QA after system-level changes.

## External evidence
- Storybook accessibility testing: https://storybook.js.org/docs/writing-tests/accessibility-testing
- Storybook UI/component testing: https://storybook.js.org/docs/writing-tests
- OpenAI Harness Engineering: https://openai.com/index/harness-engineering/

## Agreements
- Static linting catches only a subset of system quality problems.
- Accessibility automation is a first line, not a complete accessibility audit.
- Rendered component/page states need interaction and visual checks.
- Knowledge freshness, cross-links and coverage are legitimate mechanically enforceable quality dimensions for agent-oriented repos.

## Decisions
1. Doctor reports categories rather than one undifferentiated pass/fail result.
2. v0.3 statically checks structure, token leaks, component duplication, basic accessible-name heuristics and research provenance.
3. Rendered accessibility, keyboard, responsive and visual regression are explicitly next-layer checks.
4. Golden evals measure planner behavior now and will expand to component adoption, token compliance, blueprint drift and repair turns.
